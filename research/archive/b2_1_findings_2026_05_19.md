# B.2.1 Findings — eager prefill restructure on qb2 TP — 2026-05-19

## Bottom line

**`per_position_list` mode SHIPS as B.2.1.** Top-1 5/5 agreement vs the
decode-loop reference. Per-position median cos 0.998. The eager-vs-traced
kernel-selection noise prevents strict bit-exactness, but the model
produces identical token predictions.

## What works

`forward_prefill_tp_inner_v2_per_position_list`:
- Step 1: per-position embed → Python list of [1, HIDDEN] tensors
- Step 2: layer-outer loop, position-inner
  - For each layer: per-position DN/Attn + per-position MLP, list of outputs
  - Next layer reads from this list directly (no concat, no slice)
- Step 3: per-position final norm + per-position LM head (production:
  only last position)

Per-position validation vs decode-loop reference:

| pos | cos |
|---|---|
| 0 | 0.9956 |
| 1 | 0.9984 |
| 2 | 0.9996 |
| 3 | 0.9982 |
| 4 | 0.9675 |

Top-1 agreement: **5/5**. max_abs_diff: 4.0 (bf16 noise scale).

## What doesn't work

`forward_prefill_tp_inner_v2_sequential_via_slices` and
`forward_prefill_tp_inner_v2_batched_mlp`: BOTH FAIL with bit-identical
bad numbers (pos 0 cos=1.0 perfect; pos 1-4 = 0.47-0.93 noisy).

Root cause: slice+concat round-trip on TILE_LAYOUT `[1, HIDDEN]` tensors.

When you concat N `[1, HIDDEN]` TILE_LAYOUT tensors along dim=0:
- Each input is tile-padded to `[32, HIDDEN]` physical (single tile high,
  one logical row, 31 rows padding)
- The concat result's logical shape is `[N, HIDDEN]` but the physical
  storage doesn't pack logical rows tightly — they end up at tile-boundary
  positions
- Slicing logical row `pos` from the concat result returns the wrong data
  for `pos > 0` (returns padding from the next physical position, not
  the second concat'd input)

Confirmed by removing slice/concat entirely (per_position_list mode):
errors drop from min cos 0.47 to min cos 0.97, top-1 from 1/5 to 5/5.

## Debugging trace

1. First B.2.1 attempt (batched_mlp): FAIL min cos 0.47. Initial hypothesis:
   batched MLP differs from per-row MLP.
2. Added sequential_via_slices mode (same plumbing but per-position MLP):
   bit-identical bad results. Ruled out batched MLP. Bug was in common path.
3. Initial readback fix `[0]` → `[:seq_len]`: no change in numbers. Ruled
   out readback. (Aside: ConcatMeshToTensor on a REPLICATED tensor may
   return the single-chip view rather than concatenated — needs more
   investigation, but irrelevant for B.2.1 since per_position_list reads
   one position at a time.)
4. per_position_list mode (no slice/concat at all): jumped to top1 5/5,
   median cos 0.998. Confirmed slice/concat as the bug.

## Cost of per_position_list

The Python list approach has zero per-step overhead vs slice/concat: no
extra ttnn allocations for the unified `[seq_len, HIDDEN]` tensor. But
the per-position DN/Attn calls still each have full ttnn dispatch
overhead, so the wall time benefit of "prefill" over decode-loop is
small at this stage.

Wall times from probe (seq_len=5):
- decode-loop reference: 1824 ms (HF-validated production path)
- per_position_list test: 1503 ms (~18% faster)

The win is real but modest. Real prefill benefit comes from B.2.2 (parallel
attention) and B.3 (Neumann chunked DN), which actually batch ops.

## Implications for B.2.2 (parallel attention)

Parallel attention needs `[seq_len, n_heads, head_dim]` Q/K/V tensors,
which is exactly the kind of multi-row TILE_LAYOUT structure that broke
B.2.1's batched_mlp. So **slice/concat must be fixed before B.2.2**.

Candidate fixes (need a probe to pick the right one):
1. **Pre-allocated [seq_len, HIDDEN] tensor + ttnn.experimental.slice_write**:
   write into specific rows of a fixed-size tensor; no concat. Tile-aware
   write may avoid the padding issue. Friend uses this pattern.
2. **ROW_MAJOR layout** for the unified tensor: no tile padding, slice
   returns logical rows correctly. Cost: ROW_MAJOR ops may be slower than
   TILE_LAYOUT on Tenstorrent.
3. **Direct batched construction**: avoid building from per-position pieces;
   construct `[seq_len, HIDDEN]` once via batched embed (multi-token
   `ttnn.embedding(prompt_ids[seq_len], embed_tt)` if supported).

Recommendation: try option 3 first (cleanest, no per-position pieces to
assemble). Then validate with the same harness.

## Lesson for the user

This is exactly the kind of bug the incremental approach catches. The
common-mode failure between sequential_via_slices and batched_mlp
(bit-identical bad output) immediately localized the bug to common code
(NOT batched MLP, NOT the slice). The per_position_list isolation
confirmed the diagnosis cleanly.

Had we built the full B.2 (parallel everything) in one commit and run
the harness at the end, we'd have a 400-LoC diff to bisect through.
Instead, we localized to a known-narrow primitive (slice/concat on
multi-row TILE_LAYOUT) and have a clear path to fix.
