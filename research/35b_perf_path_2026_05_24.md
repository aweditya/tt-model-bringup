# 35B-A3B Perf Path — Decision Point (2026-05-24)

Following the q/k_norm correctness fix (commit `fd4367f`), this doc lays
out the three viable paths to performance, their costs, and recommendation.

## Confirmed measurements (post-fix)

- End-to-end decode: **480 ms/tok = 2.08 tok/s** (P0 baseline, [[research/35b_perf_baseline_postfix]])
- Block shares: **MoE 68.3% / DN 26.7% / ATTN 5.0%** + 5% other
- B17 DN trace demo (re-validated post-cleanup): eager 4.13 ms → traced 0.72 ms = **5.71×**
- B17 full-step trace attempt: **FAILS** at `ttnn::operations::core::from_device` — MoE's host readback of `top_idxs`/`weights` is illegal in trace capture (confirmed)

## Two trace blockers in current code

### Blocker A — MoE host readback (B17-B)
`moe_forward_ttnn` does `ttnn.to_torch(top_idxs)` + `ttnn.to_torch(weights)` to
drive a Python `for k in range(TOP_K=8)` loop over expert indices. A previous
attempt to gather experts on-device via `ttnn.embedding(top_idxs, experts_table)`
blew the L1 budget: post-embedding output is ROW_MAJOR, and `ttnn.to_layout(TILE)`
on a [2048, 256] = 1 MB bf16 tensor needed 2.2 MB CB vs 1.5 MB L1 available.

### Blocker B — DN state not in-place
`dn_forward_ttnn` returns NEW `conv_state` and `recurrent_state` tensors each
call. The trace binds to specific tensor IDs at capture; subsequent
`execute_trace` calls read the SAME state tensors that were bound at capture.
For correctness across many decode steps, state must mutate IN PLACE in the
trace. Currently it doesn't. The B17 demo accepts state leak (correct
timing, wrong recurrence) over 50 iters; production can't.

## Three paths

### Path 1 — Solve Blocker A (MoE on-device dispatch)
**Goal**: full-step trace works end-to-end. Projected 480 → ~74 ms/tok = 13.5 tok/s.

**Approach options**:
- (a) Split expert weights `[2048, 256]` into 2 chunks of `[2048, 128]` — per-chunk `to_layout(TILE)` needs only ~1.1 MB CB, fits L1. Costs 2× matmuls per expert (still trace-friendly).
- (b) Pre-pack experts in a layout that avoids any post-gather `to_layout` step (e.g. uploaded as ROW_MAJOR with shape `[256, HIDDEN * 2 * INTER_CHIP]`, and find a matmul variant that takes ROW_MAJOR input — needs API check).
- (c) Avoid `ttnn.embedding` entirely; use a tile-aware indexed-gather op if one exists in the current ttnn build.

**Cost**: medium-high. The L1 issue has 3 plausible fixes; need to try each. Plus solving Blocker B too (full-step requires both).

### Path 2 — Solve Blocker B + per-DN-layer trace
**Goal**: 30 DN traces, attn + MoE eager. Projected 480 → ~370 ms/tok = 2.7 tok/s (+30%).

**Approach**: refactor `dn_forward_ttnn` to mutate state in-place using `ttnn.copy(new_state, existing_state)` or `output_tensor=` kwarg on the state-update op. Pattern is well-trodden in 27B server for KV cache (`paged_update_cache` is in-place).

**Cost**: medium. State-in-place refactor of DN is non-trivial — recurrence has a few accumulators. Per-layer trace orchestration adds overhead but is straightforward. Result is a 30% wall savings, not the big win.

### Path 3 — Tracy profiling first, then targeted ops optimizations
**Goal**: find specific op-level wins that don't require trace.

**Approach**: build Tracy-enabled ttnn at `~/tt-metal-tracy/` per `[[reference-tracy-build-qb1]]`, profile a few decode steps, look for high-cost ops with simple alternatives (e.g. matmul that should be sharded differently, ops with `compute_kernel_config` not matching the operand sizes).

**Cost**: low-medium for setup, unknown payoff. Almost certainly won't approach the trace-driven 5-10× wins because the elephant is dispatch overhead, not per-op compute. But could find some 5-10% wins for free.

## Recommendation

**Path 1 (a)** — try the chunked `to_layout` fix first. It directly addresses
Blocker A with the smallest restructuring. If it works, we still need
Blocker B for state-in-place, but we'd be on the trajectory to 13.5 tok/s.
If chunked `to_layout` also hits L1, fall back to (b) or (c). If all three
of (a)/(b)/(c) fail, switch to Path 2 (gives us a real 30% win and validates
in-server trace integration).

**Why not Path 3 first**: per-op profiling tells us things like "matmul X
takes 0.3 ms" but we already know it's dispatch overhead summed across many
ops. Tracy is good for finding "this one op is unexpectedly slow", not for
solving "we have 1280 small dispatches per token". The architecture change
(trace) is what dispatch-bound workloads need.
